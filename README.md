# tartarus

Ad-hoc MicroVMs and systemd-nspawn containers, built from **your** flake.

Tartarus turns a small declarative host option surface (`tartarus.guests.*`,
`tartarus.proxy`) into full NixOS guest systems, a host firewall, an SSH/X509
CA, a filtering HTTP proxy, and a `tartarus` CLI to start/stop/inspect them.
The guests are ordinary NixOS systems produced by *your* packages, overlays and
secrets; tartarus provides the engine, not the content.

- **Guests are full NixOS systems.** There is no home-manager-only mode.
- **Two kinds:** `vm` (QEMU/KVM on Linux, vfkit on macOS) and `container`
  (systemd-nspawn on Linux).
- **No guest content is bundled.** Everything a guest contains comes from the
  `systemConfig` / `userConfig` you pass in.
- **Filtering proxy included.** One Squid forward proxy, no MITM, per-guest
  HTTPS/443 allowlists, proxy-only guests with all other egress dropped.
- **Standalone utilities.** `sudo-auth-proxy`, `ssh-agent-proxy` and
  `clipboard-bridge` ship as packages and self-contained NixOS/home-manager
  modules usable without any VM (see [Standalone use of the
  services](#standalone-use-of-the-services)).

## Layout

```
flake.nix              inputs + outputs (lib.mkGuests, modules, packages, checks)
lib/version.nix        tartarus's own stateVersion constant
nix/lib/               types, names, stable id -> IP/MAC/CID, mkGuests
nix/guest/             the guest engine (build/base/network/shares/proxy/...)
nix/host/              tartarus.* options, firewall, Squid proxy, CA, services
nix/packages/          the CLI + the three standalone utilities
src/tartarus/          the Python package (uv) behind the CLI
tests/                 eval-level test suite (no VM boots)
```

## Build contract: `tartarus.lib.mkGuests`

Guests are built by the **consumer's** flake, so the consumer's inputs,
overlays, packages and secrets are in scope during evaluation. `mkGuests` reads
`tartarus.guests.*` / `tartarus.proxy` from an already-evaluated host config and
returns `nixosConfigurations`, VM runner `packages`, and the stable `vmIds` map:

```nix
# in your flake's outputs
{
  inputs,
  self,
  nixpkgs,
  ...
}: let
  guests = inputs.tartarus.lib.mkGuests {
    inherit inputs nixpkgs overlays;
    system = "aarch64-linux";                    # guest system
    hostSystem = builtins.currentSystem;         # builder system
    config = self.nixosConfigurations.myhost.config;
    username = "user";
  };
in {
  nixosConfigurations = baseConfigs // guests.nixosConfigurations;
  packages.<system> = basePackages // guests.packages.<system>;
  inherit (guests) vmIds;
}
```

Result:

```nix
{
  nixosConfigurations = { "vm-<name>" = <nixosSystem>; "ctn-<name>" = <nixosSystem>; };
  packages.<guest-system> = { "vm-<name>" = <microvm runner>; };   # VMs only
  vmIds = { "<name>" = <id>; };
}
```

`mkGuests` arguments: `inputs`/`self` (optional; tartarus injects its own),
`nixpkgs`, `system`, `hostSystem`, `config`, `username`, `homeDir`, `overlays`,
`pkgs`, `hostPkgs`. It defaults `system` from `TARTARUS_SYSTEM`/`hostSystem`,
`homeDir` from `HOME`, and imports `nixpkgs` with `allowUnfree` when no `pkgs`
is given.

### Deliberate impure interface

`mkGuests` reads a few environment variables through `builtins.getEnv`, so the
consuming flake must be evaluated with `--impure`. This is the
instance/shares interface: the *same* flake attribute can produce a
differently-configured instance per invocation.

| Variable | Effect |
| --- | --- |
| `MICROVM_INSTANCE_SUFFIX` | suffix for numbered `vm spawn` instances |
| `MICROVM_ID_OVERRIDE` | forced id/CID for a numbered VM instance |
| `MICROVM_EXTRA_SHARES` | JSON list of ad-hoc `vm start --mount` shares |
| `CONTAINER_INSTANCE_SUFFIX` / `CONTAINER_ID_OVERRIDE` | same, for containers |
| `TARTARUS_HOST_UID` | invoking host uid (virtiofs ownership) |
| `HOME` | invoking host home (share sources, pubkey) |

The CLI builds VMs with
`nix build <user-flake>#packages.<system>.vm-<name> --impure` and containers
with `nixos-container create <name> --flake <user-flake>#ctn-<name>`. Its
runtime configuration lives in `~/.config/tartarus/config.toml`, generated by
the host module at rebuild time; it never points at the tartarus repo itself.

## Option surface

### `tartarus.proxy` (global transport config only)

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `enable` | bool | `false` | Enable the HTTP proxy. |
| `location` | str | `"host"` | `"host"`, or the name of an enabled `kind = "vm"` guest with `internet = true` (Linux and Darwin). |
| `port` | port | `3128` | Proxy port. |
| `listenAddresses` | null or list | `null` | Bind addresses; derived from enabled guest kinds (the `trs` bridges, or the vmnet gateway on Darwin) when null. Never loopback. |
| `log` | bool | `false` | Metadata-only logging (client IP, CONNECT host) to journald. |

### `tartarus.guests.<name>`

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `enable` | bool | `false` | Whether this guest *exists* on this host: gates the `vm-`/`ctn-<name>` flake outputs, the host-side CA cert, firewall rules, proxy entries and autostart. It does not force an eager build — builds stay lazy, on `tartarus start` / `nix build`. Disabled guests are absent from the generated `config.toml`. |
| `kind` | `"vm"` \| `"container"` | `"vm"` | Guest kind. |
| `id` | null or int | `null` | Static id 3-100 (determines IP/MAC/CID); auto-assigned from 101 when null. |
| `graphical` | bool | `false` | Graphical remote display via the `wprs` transport. |
| `internet` | bool | `true` | Direct NAT egress. Mutually exclusive with `proxy.enable`. |
| `sharedFolder` | bool | `false` | Mount a per-guest host directory at `~/shared`. |
| `shares` | list | `[]` | Extra host/guest directory shares (passed to `microvm.shares`; `proto` is normalized per platform). |
| `apps` | list | `[]` | Host `.desktop` launchers for apps running in the guest. |
| `autostart` | bool | `false` | Start on login via a tartarus user service. |
| `requires` | list | `[]` | Names of other enabled guests that must be started before this one. `tartarus start` auto-starts dependencies first. The graph must be acyclic. |
| `services.clipboardBridge` | bool | `false` | Clipboard bridge (guest client + host server, mTLS). |
| `services.sshAuthProxy` | bool | `false` | Forward the host ssh-agent into the guest. |
| `services.sudoAuthProxy` | bool | `false` | PAM sudo authentication proxy. |
| `services.disableVsock` | bool | `false` | Force TCP instead of VSOCK (no-op where VSOCK is unavailable). |
| `vm.vcpu` / `vm.mem` | int / int | `1` / `768` | VM only. |
| `vm.persistentHome.enable` / `.size` | bool / int | `false` / `5120` | VM only, writable home disk image (MiB). |
| `vm.nixStoreOverlay.size` | int | `2048` | VM only, writable `/nix/store` overlay (MiB). |
| `firewall.enable` | bool | `false` | Enable a tartarus-managed firewall. |
| `firewall.location` | `"host"` \| `"guest"` | `"guest"` | `"host"` is Linux-only; `"guest"` runs nftables inside the guest. |
| `firewall.allow` | list | `[]` | Extra host-service allowances (not an egress backdoor). |
| `proxy.enable` | bool | `false` | Route egress through the proxy (requires global `tartarus.proxy.enable`). |
| `proxy.allowHosts` | list | `[]` | Squid `dstdomain` allowlist; HTTPS/443 only. |
| `systemConfig` / `userConfig` | attrs | `{}` | Your NixOS / home-manager configuration for the guest. |

`enable` decides whether a guest is part of the host at all, not when it is
built. A disabled guest contributes no `vm-<name>`/`ctn-<name>` attribute to the
consumer flake, no host CA certificate, no firewall rule, no proxy entry and no
autostart service, and is omitted from the generated `config.toml`. The guest
closure is only realised when you build it (`tartarus start`, `vm spawn` or a
plain `nix build`), and `autostart` is an independent flag. Because the CLI
learns the guest set from `config.toml`, it can only act on enabled guests: a
disabled or unknown name is refused before any build, state-dir creation or SSH
(see [CLI](#cli)).

Tartarus also exposes host options for the CA (`tartarus.ca.*`), system SSH
trust (`tartarus.ssh.*`), and the generated CLI config
(`tartarus.flakePath`, `tartarus.stateRoot`, `tartarus.sshDir`,
`tartarus.system`, `tartarus.log`).

### Assertions (evaluation errors)

- `internet = true` and `proxy.enable = true` are mutually exclusive.
- `proxy.enable` requires the global `tartarus.proxy.enable`.
- `tartarus.proxy.location` must be `"host"` or an enabled `kind = "vm"` guest
  with `internet = true` (both Linux and Darwin).
- `firewall.location = "host"` is Linux-only.
- Static ids must be unique within a kind and in 3-100 (auto ids start at 101).

## CLI

```
tartarus list                     # every guest and whether it is running
tartarus status [name]            # detailed status
tartarus start <name>             # build (if needed) and launch in the background
tartarus build <name>             # build (if needed) without starting
tartarus spawn <template>         # an extra, independent instance
tartarus stop <name> [--purge]    # shut down (optionally delete state)
tartarus restart <name>
tartarus logs <name>              # console log / journal
tartarus ssh <name>
tartarus cid <name>               # MicroVM VSOCK CID
tartarus ip <name>                # host-reachable IP (Darwin: via ARP)
tartarus proxy <name>             # ProxyCommand helper (VSOCK)
tartarus proxy-ip <name>          # ProxyCommand helper (vmnet IP)
```

The CLI is `packages.<system>.tartarus`, run with
`nix run .#tartarus -- <args>` or installed on the host.

### The "enabled guest" guard

Every command that names a guest (`start`, `spawn`, `stop`, `restart`, `ssh`,
`status <name>`, `logs`, `cid`, `proxy`, `ip`, `proxy-ip`, plus their
`--container` variants) first checks that the name is an enabled guest. It reads
the generated `config.toml`, which is built from `tartarus.instances.guests` and
only ever contains guests with `enable = true`; presence there *is* the
"enabled on this host" predicate. A disabled or unknown name therefore fails
cleanly, before any build or state change:

```
error: guest "ghost" is not enabled on this host; set `tartarus.guests.ghost.enable = true` (kind = "vm") in your configuration and rebuild (tartarus rebuild / darwin-rebuild / nixos-rebuild).
```

Numbered instances (`vault-2`) and the `.trs` SSH suffix resolve to their base
template, and a name enabled under the *other* kind is reported as such
(`is enabled as kind "container", not "vm"`). All-guests commands (`list`,
`status` with no name) enumerate only the enabled set. This guard exists
precisely because a disabled guest has no host-side firewall rules, CA
certificate or proxy entries. See `src/tartarus/{config,cli}.py`.

## Standalone use of the services

Each utility is exposed as a package and as a NixOS **and** home-manager module,
and every module is self-contained: it needs only its own
`tartarus.<service>.*` options, `pkgs`, `lib` and
[`nix-service`](https://github.com/niozow/nix-service). None of them requires the
tartarus host module, a guest, or any VM/container — import the module and set
the options directly:

| Package | NixOS module | home-manager module | Options |
| --- | --- | --- | --- |
| `sudo-auth-proxy` | `nixosModules."sudo-auth-proxy-pam"` (or the legacy `nixosModules."sudo-auth-proxy"`) | `homeManagerModules."sudo-auth-proxy"` | client: `tartarus.sudo-auth-proxy.*`; server: `tartarus.sudo-auth-proxy.server.*` |
| `ssh-agent-proxy` | `nixosModules."ssh-agent-proxy"` (host-side server) | `homeManagerModules."ssh-agent-proxy"` (server, bridge, agent, merge) | `tartarus.ssh-agent-proxy.{server,bridge,agent,merge}.*` |
| `clipboard-bridge` | `nixosModules."clipboard-bridge"` (host-side server) | `homeManagerModules."clipboard-bridge"` (server, client, adminClient) | `tartarus.clipboard-bridge.{server,client,adminClient}.*` |

The NixOS `sudo-auth-proxy` client installs the PAM wiring (`pam_exec.so` into
the `sudo`/`login`/`su` stacks); the home-manager `sudo-auth-proxy` module runs
the server that shows the elevation dialog. To depend on just the PAM side by
name, use the explicit `sudo-auth-proxy-pam` output — it is the identical module
as `nixosModules."sudo-auth-proxy"`, kept as an alias for compatibility.

```nix
# flake.nix of a consumer that has no tartarus guests
{
  inputs.tartarus.url = "github:niozow/tartarus.nix";
  # ...
  nixosConfigurations.client = nixpkgs.lib.nixosSystem {
    modules = [
      inputs.tartarus.nixosModules."sudo-auth-proxy-pam"
      {tartarus.sudo-auth-proxy = {enable = true; host = "10.200.0.1"; port = 65001;};}
    ];
  };
}
```

Packages are also directly buildable: `nix build .#sudo-auth-proxy`,
`.#ssh-agent-proxy`, `.#clipboard-bridge`. All units are created through
`nix-service`, so the same definitions work as root/user services on NixOS and
macOS. The guest halves are wired automatically when a guest sets the matching
`services.*` flag.

## Platform notes

### Linux (NixOS)

- QEMU/KVM guests; containers via systemd-nspawn.
- Two static bridges: `trs0` for VMs (`10.200.0.0/24`, host `10.200.0.1`) and
  `trs1` for containers (`10.201.0.0/24`, host `10.201.0.1`).
- VSOCK is available for VMs and is the default transport for host/guest
  services; containers and Darwin always use TCP.
- The host owns nftables. There is no `networking.firewall.*` involvement.
- A host proxy binds both bridge host addresses; a guest-hosted proxy is reached
  by direct routing (a `forward` accept plus a masquerade exception so the
  client's source IP survives for the per-guest `src` ACLs).
- A proxy-only guest can reach only the proxy; DNS (53), SSH (22) and plain
  HTTP (80) are dropped, and the allowlist is HTTPS/443-only.

### macOS (nix-darwin)

- vfkit guests on `vmnet-shared` NAT (`192.168.64.0/24`, gateway
  `192.168.64.1`). No host bridge, no VSOCK, no host nftables.
- The bridge's `vmenet` ports are flagged `PRIVATE`: guests reach the host but
  **not each other**, so a guest-hosted proxy is exposed through a host
  `socat` relay on `192.168.64.1:3128` (clients target the gateway). The relay
  terminates the connection, so Squid sees the gateway as the client and the
  per-guest ACLs collapse into one relay client with a unioned allowlist.
  DNS uses the host resolver on `.1:53`.
- Guests get deterministic static addresses (`192.168.64.<id + 42>`); DHCP is
  broken under vfkit.
- All host/guest services use TCP. `tartarus proxy-ip` resolves the guest from
  the host ARP table via its deterministic MAC (falling back to the
  deterministic address), since guests send no gratuitous ARP.
- A guest can opt into an in-guest nftables firewall (a practical policy, not a
  hard boundary).
- Building Linux guests needs `nix.linux-builder` (tartarus enables it by
  default on Darwin); see nixcfg's `docs/linux-builder.md`.

## Tests

The eval-level suite boots nothing and builds nothing:

```bash
nix eval --impure --file tests/default.nix --json     # standalone
nix flake check --all-systems --impure --no-build     # via checks.<system>
```

It covers the option assertions, stable id assignment, the rendered Squid
config, nftables snapshots for the full internet x proxy matrix (including the
proxy accept living in the same guest input chain, and cross-kind routing), the
generated `environment.d` proxy variables, and `mkGuests` output names/ids. See
`docs/smoke.md` for the manual, per-platform smoke list.
